# Отчёт о качестве данных

## 1. Введение

Для лабораторной работы использован учебный синтетический датасет заказов небольшой сети кофеен `coffee_shop_sales.csv`. Он содержит сведения о дате заказа, товаре и его категории, городе, способе оплаты, канале продаж, размере, цене, количестве, скидке, возрасте клиента, рейтинге, времени доставки и выручке.

Условным заказчиком анализа является управляющий сетью кофеен. Данные подходят для описательной аналитики (сравнение продаж по товарам, категориям, городам и каналам), поиска аномалий, а также предварительного изучения факторов, связанных с выручкой и рейтингами. Поскольку датасет синтетический, обнаруженные особенности нельзя автоматически переносить на реальный бизнес.

## 2. Паспорт датасета

Размер исходного набора — **855 строк и 15 столбцов**. В нём есть дата, числовые и категориальные признаки, поэтому минимальные требования к объёму и составу данных выполняются.

| Признак | Смысл |
|---|---|
| `Order_ID` | Идентификатор заказа |
| `Order_Date` | Дата заказа |
| `Product`, `Category` | Товар и его категория |
| `City` | Город |
| `Payment` | Способ оплаты |
| `Channel` | Канал продаж |
| `Size` | Размер позиции |
| `Unit_Price` | Цена единицы |
| `Quantity` | Количество единиц |
| `Discount` | Скидка |
| `Customer_Age` | Возраст клиента |
| `Rating` | Оценка заказа |
| `Delivery_Min` | Время доставки в минутах |
| `Revenue` | Выручка по заказу |

## 3. Основные проблемы качества данных

### 3.1. Пропуски

| Признак | Пропусков | Доля строк |
|---|---:|---:|
| `Delivery_Min` | 662 | 77,43% |
| `City` | 29 | 3,39% |
| `Rating` | 21 | 2,46% |
| `Discount` | 15 | 1,75% |

Наибольшая доля пропусков наблюдается в `Delivery_Min`. Это может быть связано с тем, что время доставки не фиксируется для заказов, полученных не через доставку. Перед импутацией нужно проверить связь пропусков с `Channel`. Пропуски `Rating` и `City` также требуют внимания, поскольку могут повлиять на сравнение клиентского опыта и географии продаж.

### 3.2. Дубликаты

Обнаружено **5 полностью дублирующихся строк**. Их следует проверить перед удалением. Дополнительно проверяется уникальность `Order_ID`: повторяющийся идентификатор может означать повторную запись или особенность структуры данных, поэтому решение зависит от правил формирования заказов.

### 3.3. Неоднородные категории

В `City` встречаются варианты написания одного названия с разным регистром и пробелами, например `Berlin`, `BERLIN` и ` berlin`. Из-за этого одна категория может учитываться как несколько. Аналогичную проверку следует выполнять для `Channel`, `Product` и других текстовых полей. Нормализацию нужно выполнять на копии данных, сохраняя исходные значения для контроля.

### 3.4. Выбросы и подозрительные значения

Для `Revenue` применён метод межквартильного размаха (IQR). Получены границы примерно **от −7,26 до 32,40**, выше верхней границы находятся **28 наблюдений**. Нижняя граница отрицательна, но сама выручка в наборе положительна. Выбросы не следует удалять автоматически: крупная выручка может соответствовать реальному заказу, а может быть следствием ошибочного количества или цены. Необходима проверка исходных полей и правил расчёта.

Также следует отдельно проверить необычно большие значения `Quantity` и `Unit_Price`, поскольку они непосредственно влияют на выручку.

### 3.5. Типы шкал

Большинство категориальных признаков (`Product`, `Category`, `City`, `Payment`, `Channel`) имеют номинальную шкалу. `Size` имеет порядковую шкалу. `Rating` также следует трактовать как порядковый признак, если не доказано, что расстояния между оценками равны. Цена, количество, скидка, возраст, время доставки и выручка относятся к шкале отношений. Для `Order_Date` осмысленны интервалы между датами.

Для номинальных признаков корректна мода, но среднее и медиана не имеют содержательного смысла. Для порядковых признаков можно использовать медиану и моду, однако среднее числовых кодов требует обоснования равенства интервалов.

## 4. План улучшения качества

1. Проверить 5 полных дубликатов и повторения `Order_ID`; удалить только подтверждённые повторные записи.
2. Нормализовать текстовые категории (пробелы, регистр) в отдельных очищенных столбцах и сверить число категорий до и после обработки.
3. Изучить механизм пропусков `Delivery_Min`, `Rating`, `City` и `Discount`; не заменять все пропуски одним способом.
4. Для `Delivery_Min` учитывать, что отсутствие времени может быть структурным для заказов без доставки.
5. Проверить экстремальные `Quantity`, `Unit_Price` и `Revenue` по исходным записям.
6. Для моделирования сравнить исходную выручку с `log1p` или квадратным корнем; винзоризацию применять только с сохранением исходного столбца и фиксацией выбранных квантилей.
7. Повторить аудит и визуализации после очистки, чтобы убедиться, что обработка не создала новых искажений.

## 5. Краткое резюме

В ходе первичного анализа оценены структура и типы признаков, пропуски, дубликаты, подозрительные значения и распределения. Выявлены пропуски, неоднородное написание категорий, полные дубликаты и 28 верхних выбросов по выручке.

Главный вывод — проблемные значения нельзя обрабатывать механически. Перед удалением, заменой или преобразованием нужно выяснить возможную причину их появления и учитывать предметную область. Датасет пригоден для учебного разведочного анализа, но перед построением моделей требует документированной очистки и проверки предположений о пропусках.
